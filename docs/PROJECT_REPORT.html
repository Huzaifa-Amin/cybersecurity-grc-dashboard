01 · Executive summary

Northstar brings a compact control register and a role-aware dashboard together for one organization's GRC work. It helps teams see who owns a control, how mature it is, what risk remains, when remediation is due, and where supporting evidence is held.

Illustrative starter records reference NIST CSF 2.0, ISO 27001 Annex A, NIS2, and GDPR. They are examples, not authoritative framework mappings. Teams can add their own domains, mappings, owners, maturity scores, due dates, and evidence references.

02 · Architecture & component responsibilities

The browser connects to the Streamlit application. The app authenticates a named account, checks its role, validates submitted fields, and reads or writes through SQLAlchemy. PostgreSQL is the shared Docker Compose database; a local SQLite file keeps development and tests simple.

ComponentResponsibility
app.pySign-in, first-admin setup, filters, metrics, register forms, exports, account administration, and audit display.
security.pyUsername/password validation, salted password hashing, password verification, and reusable permission predicates.
store.py + AlembicVersioned SQLAlchemy schema, database initialization, seeded examples, field validation, persistent CRUD, and audit events.
risk_engine.pyMaturity aggregation, framework counts, risk summaries, and priority ordering.
PostgreSQL / SQLitePostgreSQL is shared Compose storage; SQLite is the local development and test adapter.

03 · Data model and tables

Alembic applies versioned schema migrations on application startup. An empty control table is seeded once with the illustrative register. Users are never seeded with a shared default password; the first administrator is created by a setup flow requiring an operator-configured bootstrap token.

TableMain columnsPurpose and safeguards
usersid, username, display_name, password_hash, role, is_active, must_change_password, auth_version, created_atNamed local accounts. Unique usernames, constrained role values, salted password hashes, account disablement, forced temporary-password change, and session invalidation after account/password changes.
controlsid, control, domain, framework, owner, status, status_score, risk_level, due_date, evidence, noteUnique control register. Database checks constrain risk, status, and maturity; application validation checks required text and ISO dates.
audit_logid, actor_username, action, entity_type, entity_id, details, created_atAppend-only application events for control changes, account changes, and password changes. Visible to administrators.
app_settingskey, valueStores the one-time sample-data seed marker so an intentionally emptied register stays empty after restart.
alembic_versionversion_numMigration framework metadata that records the schema revision applied to this database.
Evidence handling: evidence fields hold references such as a restricted document ID, ticket, or repository path. The application does not upload, scan, or store evidence files.

04 · Least-privilege access model

Every authenticated action is associated with a named user. Permissions are intended to follow the work required now; administrators can change a user's role or deactivate an account when that need ends.

CapabilityViewerEditorAdministrator
View filtered dashboard and control registerYesYesYes
Export filtered register to CSVYesYesYes
Create or update control recordsNoYesYes
Delete control recordsNoNoYes
Create, change, or deactivate user accountsNoNoYes
Read the application audit historyNoNoYes

Passwords require at least 12 characters and are stored as PBKDF2-HMAC-SHA-256 hashes with a random 16-byte salt and 600,000 iterations. There is no default account. A bootstrap token gates the first administrator. New accounts and administrator-reset accounts must change their temporary password before opening the dashboard. The application prevents demoting or disabling the last active administrator. Account or password changes increment an authentication version so existing sessions are rejected on their next request.

Operational boundary: application-managed passwords do not provide SSO, MFA, e-mail verification, or self-service recovery. Administrators can reset another user's password; secure transfer of the temporary credential is an organizational responsibility. Use an identity provider when organizational policy requires stronger identity controls.

05 · Main workflows

InitializeThe app creates its tables and seeds sample controls only when the register is empty.
Claim administrationThe operator sets a bootstrap token out of band; the first administrator enters it during one-time setup.
Provision least privilegeAn administrator creates individual accounts, assigns viewer, editor, or administrator access, and the user replaces their temporary password at first sign-in.
Assess controlsEditors maintain ownership, status, scores, risk, due dates, evidence references, and remediation notes.
Review and prioritizeUsers filter by framework, domain, risk, and search text; dashboard calculations follow the visible selection.
Export and auditAny role can export the filtered register as CSV; formula-like text is neutralized for spreadsheet use, and administrators can review recent changes.

06 · Scoring and interpretation

Control maturity

Average maturity = sum(status_score for selected controls) / count(selected controls)

The result is rounded to one decimal place. An empty selection reports 0.0. Each record's maturity score is an editor-entered value from 0 to 100; the application does not infer it from status text.

Priority score

Priority = (risk severity index x 25) + (100 - status_score)
Severity index: Low=0, Moderate=1, High=2, Critical=3

Higher values sort first. This transparent heuristic favors higher residual risk and lower maturity; it is not a quantitative likelihood-impact model. The overdue indicator counts controls whose due date is before today and whose status is not Implemented. Filters affect the dashboard metrics and risk lists.

08 · Installation, deployment, and maintenance

Local development uses SQLite at ./data/grc_dashboard.db. Docker Compose starts one Streamlit service and one PostgreSQL 16 service with a persistent named volume. The app container runs as an unprivileged user and drops Linux capabilities. Compose binds the dashboard to 127.0.0.1:8501 by default.

Operational checklist

  • Configure unique random values for POSTGRES_PASSWORD and BOOTSTRAP_ADMIN_TOKEN in an ignored local .env; do not commit secrets.
  • For remote users, front the service with TLS and a restricted reverse proxy; preserve Streamlit's XSRF protections.
  • Back up PostgreSQL regularly, test restores, and protect backup files to the same standard as the database.
  • Review administrator assignments and account status periodically; deactivate accounts no longer required.
  • Monitor logs, database health, disk capacity, dependency/security advisories, and failed deployment health checks.
  • Keep evidence files in an approved document-management system and enter only a safe reference in Northstar.

Useful commands

docker compose up --build -d
docker compose ps
docker compose logs -f grc-dashboard
docker compose exec -T database pg_dump -U grc_dashboard grc_dashboard > backup.sql

The deployment has one application process and no horizontal scaling, queue, cache, or dedicated monitoring service. Its target user count is a design goal, not a measured capacity promise; validate concurrency, backups, and recovery in the target hosting environment.

09 · Security model, risks, and limitations

ConcernCurrent mitigationRemaining responsibility
Unauthorized account accessNamed accounts, salted password hashes, role checks, bootstrap token, account deactivation.Enforce TLS and network restrictions; no MFA or identity-provider integration.
Over-privileged usersViewer/editor/administrator capability split and protected last administrator.Assign roles to work needs and review them routinely.
Unauthorized or invalid writesParameterized SQLAlchemy operations, field validation, database constraints, audit events.Application audit events are not a tamper-proof external audit service.
Loss or exposure of recordsPostgreSQL persistent volume; Compose port is localhost-bound by default.Configure encrypted backups, restore tests, storage controls, and production TLS/reverse proxy.
Evidence leakageOnly a text reference is stored; no file upload functionality.Use approved access-controlled evidence storage; do not put secrets or sensitive evidence in notes.
Incorrect compliance conclusionReport labels starter mappings and scores as decision support.Validate framework applicability, evidence, and legal interpretations with qualified reviewers.

Known gaps: no SSO/MFA, e-mail invitations or self-service recovery, rate limiting backed by shared storage, evidence-file upload, immutable audit export, multi-tenant isolation, or load/performance test. The app is intended for one organization and a single app instance. Review SECURITY.md and the threat model before deployment.

10 · Verification and acceptance criteria

The automated test suite covers score aggregation, framework mapping, one-shot risk iterables, database seeding and CRUD, input validation, password hashing/authentication, role behavior, administrator protection, and audit ordering. CI additionally runs Ruff, Black, and a dependency audit.

Acceptance areaExpected behavior
PersistenceCreated and edited controls remain after app reruns/restarts using the configured shared database.
Least privilegeViewer cannot edit; editor cannot delete or manage accounts; administrator can manage users and delete records.
Input and export safetyInvalid risk/status values, dates, scores, and required fields are rejected; formula-like text is neutralized in CSV exports.
AuditabilityControl and account changes create an event with actor, action, entity, and timestamp.
First runNo default admin is created; setup remains locked without an operator-provided bootstrap token.
ReportingDashboard values and CSV data follow the selected filters.
